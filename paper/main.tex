\begin{abstract}
We present SWE-P-Bench, a benchmark for evaluating large language models on real-world software engineering tasks drawn from high-energy physics (HEP) Python libraries.
The benchmark comprises 50 curated instances from three Scikit-HEP repositories---\texttt{pyhf}, \texttt{awkward-array}, and \texttt{Uproot}---each consisting of a GitHub issue, a gold patch that resolves it, and automatically generated oracle tests that verify the fix.
We describe the automated pipeline for instance construction, including LLM-based oracle synthesis with FAIL$\to$PASS validation, and report baseline results using Claude Sonnet.
\end{abstract}

\section{Introduction}

SWE-bench~\cite{jimenez2024swebench} demonstrated that real GitHub issues provide a rigorous evaluation framework for code-generating LLMs.
However, the original benchmark focuses on general-purpose Python libraries.
Domain-specific codebases---particularly in scientific computing---present unique challenges: specialised APIs, mathematical invariants, and testing patterns that differ from typical web or systems code.

SWE-P-Bench adapts the SWE-bench methodology to high-energy physics, targeting the Scikit-HEP ecosystem.
Our contributions are:
\begin{enumerate}
    \item A curated benchmark of 50 instances across 3 HEP repositories, with verified gold patches and automatically generated oracle tests.
    \item An automated pipeline for benchmark construction that uses LLM-synthesised oracles with a validate-and-retry loop.
    \item Baseline solve rates for Claude Sonnet on domain-specific software engineering tasks.
\end{enumerate}

\section{Methodology}

\subsection{Pipeline Overview}

Our benchmark construction pipeline consists of six stages:

\begin{enumerate}
    \item \textbf{Scrape}: Identify GitHub issues with linked, merged pull requests from target repositories.
    \item \textbf{Filter}: Apply heuristic (data-entry detection) and LLM-based (relevance scoring) filters to remove unsuitable instances.
    \item \textbf{Oracle Generation}: For each candidate, use Claude Sonnet to generate pytest oracle tests. Each test is validated in-place: the repository is cloned at the base commit, the tests must FAIL before the gold patch and PASS after it (the FAIL$\to$PASS invariant). Failed attempts receive structured pytest output as feedback, with up to 3 retry attempts.
    \item \textbf{Gold Re-validation}: The FAIL$\to$PASS check from Step 3 is re-run independently in a fresh clone. This catches flaky or environment-dependent tests: in practice, 43.5\% of oracles that passed initial validation fail to reproduce, making this step essential for benchmark quality.
    \item \textbf{Quality Review}: LLM-based assessment of causal connection, test relevance, and test robustness for each (issue, patch, test) triplet.
    \item \textbf{Assembly}: Select the final 50 instances with balanced repository representation.
\end{enumerate}

\subsection{Oracle Test Synthesis}

Oracle tests are generated by prompting Claude Sonnet with the issue description and gold patch.
Each test must:
\begin{itemize}
    \item \textbf{FAIL} when run against the base commit (before the fix).
    \item \textbf{PASS} when run against the patched code (after the fix).
    \item Be self-contained, deterministic, and test only the described behaviour.
\end{itemize}

The validator clones the repository at the base commit, installs it, runs the generated tests before and after applying the gold patch, and checks the FAIL$\to$PASS invariant.
Failed attempts receive structured feedback (which tests passed/failed incorrectly, pytest output) that accumulates across retries.

\subsection{Quality Review}

Each gold-passing instance is reviewed by Claude Sonnet on three axes (1--5 scale):
\begin{itemize}
    \item \textbf{Causal Connection}: Does the PR directly fix what the issue describes?
    \item \textbf{Test Relevance}: Do the oracle tests test the behaviour from the issue?
    \item \textbf{Test Robustness}: Are tests deterministic and testing observable behaviour?
\end{itemize}
Instances are accepted if all scores $\geq 3$ and the average $\geq 3.5$.

\section{Discussion}

Claude Sonnet achieves a 42.0\% solve rate on SWE-P-Bench, substantially higher than the $\sim$20\% baseline we expected from general-purpose SWE-bench results.
Several factors may explain this:

\textbf{Repository-level variation.}
Performance varies dramatically across repositories: 54.5\% on pyhf, 25.0\% on awkward, and 11.1\% on uproot5.
pyhf issues tend to involve configuration, API surface, or numerical changes in a well-structured pure-Python codebase, which are more amenable to single-shot patching.
awkward and uproot5 involve lower-level array manipulation and I/O code with more complex dependencies.

\textbf{Oracle quality.}
Our oracle synthesis pipeline achieves a 34.3\% valid oracle rate from filtered candidates, with 84.1\% of gold-passing instances accepted by quality review.
The strict FAIL$\to$PASS invariant combined with multi-axis quality review ensures that accepted instances genuinely test the described behaviour.

\textbf{Limitations.}
The benchmark is skewed toward pyhf (33/50 instances) due to higher oracle generation yield.
The awkward repository's C++ compilation requirements for older commits limited oracle generation coverage.
Claude Sonnet subscription CLI timeouts caused 3 of 8 awkward solver attempts to produce empty patches.
Future work should expand coverage to additional repositories and include multi-turn solver strategies.

\section{Conclusion}

SWE-P-Bench provides the first SWE-bench-style benchmark targeting high-energy physics codebases.
Our automated pipeline---from GitHub scraping through LLM oracle synthesis to quality review---produces verified benchmark instances without requiring hand-written tests.
On 50 curated instances across three Scikit-HEP repositories, Claude Sonnet achieves a 42.0\% single-shot solve rate, with notable variation across repositories.
This benchmark enables systematic evaluation of LLM coding capabilities on domain-specific scientific software.
